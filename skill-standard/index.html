    • 결과 JSON과 HTTP 응답 예시: 실제로 실행해서 얻은 출력. 실행한 날짜를 함께 적음

1 개요

1.1 표준화 범위

  • clinical-agent의 통계 분석은 LLM이 R 코드를 써서 돌리는 방식이 아님. 미리 검증해 등록한 분석 단위만 실행
  • 이 단위가 Agent Skill(이하 Skill). 통계 분석 방법 하나가 Skill 하나
  • agent는 요청을 읽고 어떤 Skill을 어떤 인자로 부를지만 정함
  • 실제 계산은 R 실행 서비스가 등록된 Skill의 R 함수를 불러 수행

표준화한 것:

  • Skill을 기술하는 형식
    • Skill마다 YAML 명세 한 개
    • 정해진 필드에 적는 것: 입력 인자의 형식, 데이터 검증 규칙, 실행 조건, 출력 표의 이름과 열, 오류 코드별 처리 방식, 결과 검수 기준, 예제
    • 필드는 JSON Schema(registry/schema/skill.schema.json)로 정의 → 형식이 틀린 명세는 등록부 점검에서 걸림
  • 실행 방식
    • 모든 Skill이 같은 실행 틀(r-executor/R/core.R)을 거침
    • 실행 틀은 명세를 읽어 데이터셋을 허용 목록에서 찾고 인자 검증, 검증 규칙·실행 조건 점검을 마친 뒤에야 wrapper 함수를 부름
    • 결과는 표·그림·주석·경고·오류·출처 정보로 이루어진 같은 구조 → agent는 Skill마다 다른 코드를 둘 필요 없음
  • 등록 절차
    • Skill 하나를 추가하려면 명세, wrapper, 테스트, 예제 데이터를 갖춰야 함
    • 등록부 생성기(registry/build_registry.R)가 이것들을 대조해 문제가 없을 때만 통과
    • 생성기가 함께 만드는 것: 사람이 읽는 요약(REGISTRY.md), 항목별 상세 등록부(registry.xlsx), agent가 읽는 기계용 등록부(registry.json)

1.2 Skill의 네 구성요소

  • Skill 한 종은 아래 네 가지로 이루어짐. 하나라도 빠지면 등록부 점검을 통과하지 못함
  • 예제 데이터는 이미 허용 목록에 있는 데이터셋을 쓰면 새로 만들지 않음
구성요소 위치 하는 일
명세 registry/skills/<ID>.yaml 입력·검증 규칙·실행 조건·출력·오류·검수 기준·예제를 적음. 실행 틀과 agent가 모두 읽음
R wrapper r-executor/R/skills/<계열>.R의 skill_<계열>_<방법>(data, p) 검증을 마친 인자로 실제 분석 함수를 부르고 결과를 표·그림으로 정리
테스트 r-executor/tests/testthat/test-<ID>.R 정상 사례: 결과표 값을 독립적으로 계산한 기준값과 대조. 오류 사례 2개 이상: 정의한 오류 코드로 막히는지 확인
예제 데이터 r-executor/R/datasets*.R의 허용 목록 R 패키지에 들어 있는 공개 자료를 정해진 전처리로 읽음. 명세의 examples가 이 ID를 씀
  • 명세와 wrapper는 implementation 필드로, 명세와 테스트는 tests 필드로 이어짐
  • 데이터셋은 ID로만 가리킴. 실행 틀은 허용 목록에 없는 ID나 파일 경로를 받지 않음

1.3 등록부를 쓰는 곳

  • 등록부는 문서용 목록이 아님. 시스템 여러 곳이 실제로 읽는 기준

읽는 곳:

  • R 실행 서비스: 시작할 때 registry/skills/*.yaml을 모두 읽음
    • 명세에 없는 Skill ID는 실행하지 않음
    • 명세에 없는 인자는 거부
    • 명세의 규칙과 오류 정의대로 막거나 경고
  • agent: registry/registry.json을 읽어 LLM에 줄 도구 정의를 만듦
    • Skill ID → 도구 이름, 기능명·분석 방법·설명 → 도구 설명, 입력 정의 → 도구 인자 schema
    • 실행을 요청할 때 등록부의 버전을 함께 보냄. R 실행 서비스의 버전과 다르면 실행되지 않음(섹션 12)
  • 분석계획 검증: 계획에 든 분석마다 R 실행 서비스의 /validate를 불러 명세의 입력 정의와 규칙으로 미리 점검
    • 사용자가 직접 낸 계획과 agent가 만든 계획이 같은 검증을 거침
  • 시험 실행기(eval/kaic_suite.py)
    • 등록부의 예제로 Skill 실행
    • 명세의 출력 표 열 목록과 실제 결과를 기계적으로 대조
    • 입력 정의에서 오류 입력을 자동으로 만들어 명세의 오류 코드와 action대로 막히는지 확인(섹션 15)

결과:

  • 명세를 고치면 → 실행 동작, LLM이 보는 도구, 시험 판정에 동시에 반영
  • 명세와 wrapper가 어긋나면(예: 명세에 없는 열을 wrapper가 내면) → 테스트는 통과해도 시험 판정에서 걸릴 수 있음
  • 이 문서의 규칙 대부분은 이 어긋남을 막기 위한 것

2 구조와 실행 흐름

2.1 저장소 배치

  • Skill 관련 파일은 세 폴더에 나뉨. 아래는 이 문서가 다루는 범위만 추린 것
registry/
  skills/<ID>.yaml            Skill 명세(Skill마다 1개)
  schema/skill.schema.json    명세 JSON Schema
  build_registry.R            등록부 점검·생성기
  inventory.R, inventory.csv  기보유 함수 목록과 그 생성 스크립트
  REGISTRY.md, registry.xlsx, registry.json   생성물(직접 고치지 않는다)
r-executor/
  R/core.R                    공통 실행 틀(입력 검증, 공통 규칙, 실행, 결과, 그림 저장)
  R/isolate.R                 별도 R 프로세스 실행과 제한 시간
  R/load.R                    로더(실행 틀과 모든 wrapper를 읽는다)
  R/datasets.R, R/datasets_<계열>.R   데이터셋 허용 목록
  R/skills/<계열>.R           wrapper 함수와 계열 전용 규칙
  plumber.R, serve.R          R 실행 서비스 API와 기동 스크립트
  tests/testthat.R            전체 테스트 실행(JUnit 결과 기록)
  tests/testthat/helper-skills.R, test-<ID>.R
  install_packages.R, Dockerfile, DESCRIPTION
agent/clinical_agent/
  tools.py                    등록부 → LLM 도구 정의
  runner.py                   통계실행 agent(2단계 도구 선택)
  loop.py                     도구 호출 루프(오류 전달, 감사 기록)
  executor.py                 R 실행 서비스 클라이언트
  workflow.py                 분석계획 검증·실행
  • r-executor/R/datacheck.R(데이터 검증)와 upload.R(업로드 자료 가명처리)도 같은 로더로 읽힘. Skill 작성과는 직접 관계가 없어 이 문서에서 다루지 않음

load.R이 파일을 읽는 방식:

  • 읽는 순서(모두 전역 환경에): core.R → isolate.R → datacheck.R → upload.R → datasets.R → datasets_*.R(이름순) → skills/*.R(이름순)
  • 저장소에 .r-lib 폴더가 있으면 그 라이브러리를 맨 앞에 둠
  • 모든 파일이 같은 전역 환경을 씀
    • 그래서 가능한 것: 계열 파일이 rule_funs에 규칙 덧붙이기, 다른 계열 파일의 도우미 함수를 실행 시점에 부르기(예: km.R이 cox.R의 cox_surv()를 씀)
    • 파일을 읽는 순간(최상위 코드)에 다른 계열 파일의 함수를 부르면 그 파일이 아직 읽히지 않았을 수 있음 → 최상위에는 함수·목록 정의만 둠
  • 같은 이름을 두 파일이 정의하면 나중 파일이 조용히 덮어씀 → 등록부 생성기가 이름 충돌을 점검(섹션 10)

2.2 구성요소 간 호출 흐름

  • R 실행 서비스와 agent가 읽는 파일이 다름(주의)
    • R 실행 서비스: YAML 명세를 직접 읽음
    • agent: 생성기가 만든 registry.json을 읽음
  • 명세를 고친 뒤 생성기를 다시 돌리지 않으면
    • agent는 예전 명세로 도구를 만듦
    • 버전이 바뀐 경우에는 R 실행 서비스가 실행을 거부(E_VERSION_MISMATCH, 섹션 12)
  • 컨테이너 배포도 같음
    • R 실행 서비스 image에는 registry/skills와 r-executor/R을, agent image에는 registry/registry.json을 복사해 넣음
    • Skill을 추가하거나 고친 뒤에는 두 이미지를 모두 다시 빌드

2.3 실행 틀의 단계

  • R 실행 서비스의 /run은 core.R의 run_skill(skill_id, dataset_ref, params)을 부름
  • 아래 순서로 진행. 어느 단계든 오류가 나면 그 자리에서 멈추고 구조화된 오류 결과를 돌려줌

  1. 명세 찾기
    • 시작할 때 읽은 명세 목록에서 Skill ID를 찾음. 없으면 E_UNKNOWN_SKILL
  2. 데이터셋 해석
    • dataset_ref가 up_ 뒤에 16~64자리 16진수가 붙은 형식이면 업로드 자료의 정제본을 읽음
    • 그 밖에는 허용 목록(dataset_catalog)의 ID여야 함. 목록의 loader() 함수로 자료를 만듦
    • 경로나 코드는 받지 않음. 해당이 없으면 E_UNKNOWN_DATASET
  3. 입력 검증
    • 명세 inputs에 없는 인자가 들어오면 E_UNKNOWN_PARAM
    • 그다음 명세에 적힌 순서대로 인자마다 필수 여부, 형식, 범위, 열 존재, 변수 형식(dtype)을 봄
    • 빠진 선택 인자에는 명세의 default를 채움
    • 자세한 판정: 섹션 4.2
  4. 데이터 검증 규칙과 실행 조건
    • 명세의 validation 목록을 위에서부터, 이어서 preconditions 목록을 위에서부터 실행
    • 규칙이 위반을 알리면 그 규칙의 error 코드를 명세 errors에서 찾아 action대로 처리: warn이면 경고로 모으고 다음 규칙으로, warn이 아니면(block·ask_user) 그 자리에서 멈춤
    • 두 목록은 같은 방식으로 실행. 구분은 의미에 따른 것(섹션 4.3)
  5. wrapper 실행
    • 명세 implementation에 적힌 함수를 impl(data, p)로 부름. p는 3단계를 통과하고 기본값이 채워진 인자 목록
    • 실행 중 콘솔 출력과 메시지는 버림. 경고는 모아서 결과의 warnings에 넣음
    • 단 “was built under R version”, “is deprecated”, “replacing previous import”, “Registered S3 method”가 들어간 환경 메시지는 넣지 않음
    • R 수준의 timeout(R_EXECUTOR_TIMEOUT_SEC, 기본 60초)을 넘으면 E_TIMEOUT
  6. 결과
    • status = "ok"와 함께 돌려주는 것: wrapper가 돌려준 표·그림·주석, warnings(규칙 경고 + wrapper 경고 + 실행 중 잡힌 경고)
    • 성공이든 오류든 결과에는 출처 정보(provenance)가 붙음(섹션 7)
  • 같은 단계에서 5번을 빼고 1~4번만 하는 함수가 validate_skill(), API로는 /validate
  • 분석계획을 접수할 때와 데이터 검증 기능이 이것을 씀

2.4 별도 프로세스와 timeout

  • setTimeLimit()으로 거는 R 수준 제한은 R 코드가 실행되는 동안에만 끊김
  • 컴파일된 코드 안에서 멈춘 계산은 끊지 못함(geepack의 반복 추정이 2분 넘게 돌아오지 않은 사례 있음)
  • 그래서 /run은 기본적으로 isolate.R의 run_skill_isolated()로 Skill을 별도 R 프로세스(callr::r_session)에서 돌림

별도 프로세스의 동작:

  • 프로세스는 한 번 띄운 뒤 다음 요청에 다시 씀. 프로세스가 죽었으면 다음 요청 때 새로 띄움
  • 프로세스 timeout은 R_EXECUTOR_TIMEOUT_SEC보다 5초 김
    • 넘기면 프로세스를 강제 종료하고 E_TIMEOUT 오류를 돌려줌
    • 이때 출처 정보에 isolation: "process_killed"가 붙고 패키지 버전 같은 항목은 빠짐
  • 프로세스 자체에서 R 오류가 새어 나오면 프로세스를 종료하고 E_RUNTIME을 돌려줌
  • R_EXECUTOR_ISOLATE=false면 별도 프로세스 없이 같은 프로세스에서 run_skill()을 부름
  • 테스트와 등록부 생성기는 run_skill()을 직접 부름

동시 실행:

  • R 실행 서비스는 요청을 한 번에 하나씩 처리(plumber 단일 스레드)
  • 같은 R 프로세스에서 Skill 두 개를 동시에 돌리면 안 됨
    • 일부 wrapper가 기보유 패키지의 전역 데이터 조회 버그를 우회하려고 고정된 이름의 임시 전역 객체를 쓰기 때문(섹션 13)
  • 처리량은 서비스 인스턴스 수로 늘림

2.5 agent의 2단계 도구 선택

  • agent는 등록부의 Skill 하나하나를 function calling 도구로 바꿈(tools.py의 skill_to_tool())
    • 도구 이름: Skill ID
    • 도구 설명: “기능명 — 분석 방법. 설명”
    • 도구 인자: 명세 inputs에서 dataset_ref를 뺀 나머지. 데이터셋은 세션이 정한 값을 실행할 때 붙임
  • 그래서 LLM은 열 이름과 옵션만 고름. 어느 자료를 쓸지는 고를 수 없음
  • Skill이 많으면 도구 정의 전체가 프롬프트를 크게 차지 → 통계실행 agent의 기본 방식(AGENT_TOOL_MODE=routed)은 두 단계로 나눔

  • 처음에 LLM이 보는 것: 데이터셋 구조와 Skill 카탈로그뿐
  • 카탈로그는 Skill마다 한 줄: ID | 기능명 | 분석 방법 | 필수 인자 | 선택 인자
    • 인자는 이름(dtype) 꼴. dtype이 없으면 enum 값 목록이나 형식 이름을 괄호에 넣음
  • LLM은 이 줄들을 보고 load_skills로 Skill을 최대 6개까지 불러옴. 그때부터 그 Skill들의 전체 도구 정의(설명과 인자 schema)를 볼 수 있음
  • AGENT_TOOL_MODE=full이면 처음부터 모든 Skill 도구를 넘김
  • 두 방식 비교(2026-10-10, Skill 64종 상태, 시나리오 47개를 3회씩, runner.py 주석에 기록된 측정)
    • 정확도·일관성·예외 처리·오류 복구: 같음
    • 입력 토큰 중앙값: routed 17,584, full 63,228

이 구조 때문에 명세를 쓸 때 챙길 것:

  • 기능명과 분석 방법이 카탈로그에서 서로 구별되어야 함
    • LLM은 카탈로그 한 줄만 보고 후보를 고름
    • 비슷한 Skill끼리는 method에 검정 이름이나 조건을 분명히 적음(예: “Welch two-sample t-test”와 “Mann-Whitney U 검정”)
  • 설명(description)에 언제 쓰고 언제 다른 Skill을 쓰는지 적음
    • 불러온 뒤의 도구 설명에 그대로 들어감
    • 기존 명세는 “분포가 심하게 치우친 변수는 JST-TB1-MWU를 쓴다”처럼 대안 Skill ID를 적음
  • 인자 설명이 곧 LLM이 받는 인자 안내
    • 도구 인자 schema에 들어가는 것: 인자 description과 dtype(“변수 형식: numeric” 꼴로 덧붙음), values, min·max, min_items·max_items
    • default는 들어가지 않음
    • agent 시스템 프롬프트가 요청하지 않은 선택 인자를 넣지 말라고 지시 → 선택 인자는 대개 R 쪽 기본값으로 실행

LLM에 넘기는 결과:

  • Skill 결과는 LLM에 그대로 가지 않음
  • privacy guard(privacy.py의 tool_result_for_llm())가 status, skill_id, tables, notes, warnings, error만 남김. 그림은 이름과 제목만 넘김
  • 출처 정보는 LLM에 넘기지 않고 Audit Trail과 trajectory에만 남김
  • 결과표 하나가 200행을 넘으면 행 단위 자료가 섞였을 수 있다고 보고 LLM에 넘기지 않음(섹션 8.3)

3 ’종’을 나누는 기준

3.1 분석 방법 하나 = 한 종

  • Skill은 통계 분석 방법 하나를 단위로 셈. R 함수 개수가 아님
  • 한 함수가 여러 분석 방법을 수행하면 Skill도 여러 개
    • 예: jstable::CreateTableOneJS는 인자에 따라 Welch t-test, Welch 분산분석, 카이제곱 검정, Fisher 정확검정, 순위합 검정 등을 수행
    • 현재 이 함수를 부르는 Skill은 14종(CDS-ADSL-BASELINE, JSM-PS-IPTW, JSM-PS-MATCH, JST-TB1-ANOVA, JST-TB1-CHISQ, JST-TB1-DESC, JST-TB1-FISHER, JST-TB1-KW, JST-TB1-MWU, JST-TB1-NORMALITY, JST-TB1-PAIRWISE, JST-TB1-SMD, JST-TB1-STRATA2, JST-TB1-TTEST)
  • 반대로 여러 함수를 함께 불러야 하나의 분석 방법이 완성되면 그 묶음이 한 종
    • 그림을 그리는 함수와 그림에 표시한 수치를 계산하는 함수를 함께 부르는 Skill이 대부분 이 경우(r_function이 목록인 Skill이 62종)
  • 같은 함수에서 나온 Skill이 별개의 종으로 인정되려면 검증 규칙, 오류 처리, 결과 검수 기준 가운데 적어도 하나가 실제로 달라야 함
  • 인자 하나만 바꾼 복제는 종으로 세지 않음

Table 1 계열의 연속변수 비교 네 종을 명세에서 직접 뽑은 예:

ID 분석 방법(method) 그룹 범주 수 규칙 검수 기준의 기준값(acceptance.reference)
JST-TB1-TTEST Welch two-sample t-test 최소 2, 최대 2 → E_GROUP_COUNT 변수마다 stats::t.test(x ~ group, var.equal = FALSE)의 p값을 독립 계산

JST-TB1-MWU Mann-Whitney U 검정(Wilcoxon 순위합 검정) 최소 2, 최대 2 → E_GROUP_COUNT 변수마다 stats::wilcox.test(x ~ group, exact = FALSE, correct = FALSE)의 p값을 독립 계산

  • 네 Skill은 같은 함수를 부르지만 아래가 달라 각각 한 종
    • 검정 방법
    • 그룹 범주 수에 대한 규칙과 그 위반 때의 안내(예: t-test에서 3그룹이 들어오면 JST-TB1-ANOVA를 쓰라는 hint)
    • 독립 기준값을 계산하는 함수

3.2 애매한 경우의 판단 기준

  • 실제로 Skill을 나누다 보면 애매한 경우가 생김

현재 등록부가 따르는 원칙:

  • 표시 방식만 다르면 인자로 둠
    • 같은 계산에 그림 모양이나 요약 방식만 바뀌는 선택지는 별도 Skill로 만들지 않고 enum·boolean·column_list 인자로 받음
    • 예: JSM-COR-PEARSON의 추세선(line: 회귀선·LOESS·없음), JST-TB1-DESC의 nonnormal(중앙값 [IQR]로 요약할 변수 목록)
  • 항상 함께 쓰고 검증·출력이 같은 방법은 한 Skill로 묶음
    • Kaplan-Meier 생존곡선과 log-rank 검정은 같은 자료·같은 검증 규칙으로 함께 보고 → JSK-KM-LOGRANK 한 종(분석 방법: Kaplan-Meier survival curve with log-rank test)
  • 가정과 검증이 다르면 나눔
    • Pearson 상관과 Spearman 상관은 한 화면(jsmodule의 산점도 모듈)에서 나오지만 JSM-COR-PEARSON과 JSM-COR-SPEARMAN 두 종
    • Pearson: 정규성 점검 규칙(cor_normality, 경고), Fisher z 신뢰구간
    • Spearman: 동순위 점검 규칙(cor_ties, 경고), p값 계산 방식 열(p_method). 신뢰구간은 내지 않음
    • 결과표의 열과 검수 기준도 다름
  • 가중·설계 기반 분석은 별도 Skill
    • 표본설계 가중치를 쓰는 분석(JST-SVY-*, JSK-KM-SVY)은 같은 이름의 일반 분석과 따로 둠
    • 이유: 설계 변수(weights·strata·cluster·nest) 입력과 설계 전용 검증 규칙(svy_*)이 붙음. 검정 자체도 설계 기반 검정으로 바뀜
  • 출처 모듈의 버그는 옮기지 않음
    • Skill은 기보유 기능의 분석 방법을 옮길 뿐 그 구현의 버그까지 옮기지는 않음
    • 결과가 틀리는 동작은 wrapper에서 우회하고 테스트로 고정(섹션 13)
    • 출처 모듈이 임의 코드 실행(eval(parse()))으로 처리하던 기능(예: 테마 선택)은 Skill로 가져오지 않음

3.3 출처(origin)와 연결 함수(r_function)

  • Skill마다 함수 두 가지를 적음
    • origin: 이 Skill이 바탕으로 삼은 기보유 기능
    • r_function: Skill이 실제로 부르는 함수

origin 적는 법:

  • 기보유 함수 목록 registry/inventory.csv에 있는 패키지::함수여야 함(섹션 12)
  • 분석 로직이 Shiny 모듈 안에 있는 경우(jsmodule 등): 모듈 자체를 출처로 적음(예: jsmodule::rocModule, jsmodule::scatterServer)
  • 사내 Shiny 앱의 기능: openstat_app::<앱 이름> 꼴
  • 두 기능 이상을 합쳐 만든 Skill: 목록으로 적음(현재 18종)

r_function 적는 법:

  • wrapper가 부르는 함수를 적음. 출처 모듈이 내부에서 pROC::roc를 부른다면 r_function은 pROC::roc
  • 출처 모듈 코드에서 확인한 호출 방식과 기본값을 따름
  • 출처와 같은 패키지·같은 방법을 써야 함
  • 등록부 생성기가 r_function의 함수가 설치된 패키지 안에 실제로 있는지 확인

4.2.1 형식별 판정

실행 틀의 validate_inputs() 판정 순서:

  1. 명세에 없는 인자가 들어왔는지 봄. 하나라도 있으면 그 이름들을 담아 E_UNKNOWN_PARAM으로 막음
  2. 명세에 적힌 순서대로 인자를 하나씩 봄
    • 처음 걸린 인자에서 멈춤 → 필수 인자를 앞에 두는 편이 사용자에게 돌아가는 오류가 자연스러움

빠진 인자:

  • 값이 없거나(null) 길이가 0(빈 목록 [] 포함)이면 빠진 것으로 봄
    • required: true이면 E_MISSING_PARAM
    • 아니면 default가 있을 때 그 값을 채움. 없으면 인자를 비워 둔 채 넘어감
  • 기본값은 형식 검사를 거치지 않음
    • enum의 기본값이 values에 없거나 integer 기본값이 범위를 벗어나도 실행 틀과 등록부 점검 어느 쪽도 잡지 못함 → 명세를 쓸 때 직접 맞춤

값이 있을 때 형식별로 확인하는 것:

  • column: 문자열 하나여야 함(아니면 E_INVALID_VALUE). 그다음 열 이름 점검(아래)
  • column_list
    • 목록을 펼친 결과가 문자열이어야 함(아니면 E_INVALID_VALUE)
    • 개수가 min_items보다 적으면 E_MISSING_PARAM, max_items보다 많으면 E_INVALID_VALUE
    • 개수가 맞으면 원소마다 열 이름 점검
    • JSON으로 문자열 하나만 와도("age") 길이 1 목록으로 받아들임
  • enum: 값이 values에 있어야 함. 아니면 E_INVALID_VALUE이고 메시지에 허용 값이 나열됨
  • integer·number
    • 숫자 하나여야 함. integer는 정수 값이어야 함(JSON의 5와 5.0 모두 통과)
    • min·max를 벗어나면 E_INVALID_VALUE
  • boolean: true·false 하나여야 함. 문자열 "true"는 통과하지 못함
  • string: 문자열 하나여야 함. 내용은 검사하지 않음
    • 문자열을 숫자 목록 등으로 해석해야 하면 wrapper나 계열 규칙이 직접 파싱
    • 어떤 경우에도 코드로 평가하지 않음(예: roc.R의 roc_parse_cutoffs()는 쉼표로 나눠 as.numeric()만 함)
  • dataset_ref: dataset 인자 전용
    • 실행 틀은 이 정의를 인자 검증에서 빼고 agent도 도구 인자에서 뺌
    • 다른 인자에 이 형식을 쓰지 않음

열 이름 점검(column·column_list 공통) 세 단계:

  1. 이름이 R 문법에 맞아야 함(make.names(x) == x)
    • 이유: 실행 틀과 wrapper가 모형식을 reformulate()로 만듦
    • 공백이나 괄호가 든 이름은 E_INVALID_VALUE. 안내는 “변수명은 영문으로 시작하고 영문·숫자·.·_만 쓰도록 바꿔서 다시 올림”
  2. 데이터에 그 열이 있어야 함
    • 없으면 E_COL_NOT_FOUND
    • 데이터 열 이름 가운데 비슷한 이름(근사 문자열 일치, 거리 0.3 이내, 최대 3개)이 있으면 “유사 변수명: …”을 안내로 붙임
  3. 열의 값이 dtype에 맞아야 함. 맞지 않으면 E_TYPE_MISMATCH
  • dtype 판정 기준은 아래 표. dtype이 없으면 any와 같음
dtype 통과 조건
numeric R에서 숫자형(integer·double). factor는 숫자로 코딩되어 있어도 통과하지 못함
categorical factor·문자·논리형이거나, 숫자형이면서 결측 제외 값이 모두 정수이고 서로 다른 값이 10개 이하
binary 형식과 관계없이 결측 제외 서로 다른 값이 정확히 2개
any 항상 통과
  • categorical이 숫자형도 허용하는 이유: 0/1/2처럼 정수로 코딩된 범주 변수를 받아들이려고
    • 그래서 정수 값이 10종류 이하인 숫자 열은 numeric과 categorical을 모두 통과
  • 범주 수 자체를 제한하려면 dtype 대신 n_levels·max_levels 규칙을 씀

4.2.2 agent 도구 인자로 변환

  • agent는 인자 정의를 JSON Schema로 바꿔 LLM 도구 인자로 넘김(tools.py의 _input_schema())
  • 형식별 변환
    • column → 문자열
    • column_list → 문자열 배열(minItems·maxItems 포함)
    • enum → values를 허용 값으로 하는 문자열
    • integer·number → minimum·maximum이 붙은 숫자
    • boolean → 불리언
    • 그 밖 → 문자열
  • 설명에는 인자 description 뒤에 “(변수 형식: numeric)”처럼 dtype이 덧붙음
  • required: true인 인자가 도구의 필수 인자가 됨. 정의에 없는 인자는 허용하지 않음
  • default는 넘어가지 않음

4.3 데이터 검증 규칙과 실행 조건

  • validation과 preconditions는 규칙 객체의 목록
  • 규칙 객체의 필수 키: rule(규칙 이름), error(위반 때의 오류 코드, ^[EW]_[A-Z0-9_]+$). 나머지 키는 규칙마다 정해진 인자
validation:
  - {rule: n_levels, column: group, min: 2, max: 2, error: E_GROUP_COUNT}
  - {rule: max_missing_rate, columns: [vars, group], max: 0.2, error: W_MISSING_HIGH}
preconditions:
  - {rule: min_rows, columns: [vars, group], min: 4, error: E_TOO_FEW_ROWS}
  • 규칙 인자 가운데 column, columns, group은 데이터 열 이름이 아니라 Skill 입력 인자 이름
    • 위 예의 column: group은 “입력 인자 group에 사용자가 지정한 열”을 뜻함
    • columns에 column_list 인자를 넣으면 그 인자의 열 전체가 대상
    • 선택 인자를 가리키는 규칙은 사용자가 그 인자를 주지 않았으면 대개 아무것도 검사하지 않고 통과(예: 그룹 없이 실행한 상관분석의 n_levels)
  • 규칙 이름은 core.R의 공통 규칙이거나 계열 파일에 정의된 계열 전용 규칙이어야 함. 규칙마다 필수 키가 있음
    • 목록과 동작: 섹션 5
  • 등록부 점검이 문제로 잡는 것: 알 수 없는 규칙 이름, 빠진 필수 키, 명세 errors와 공통 오류 어디에도 없는 오류 코드

두 목록의 구분:

  • 실행 방식은 같음(섹션 2). 구분은 의미에 따름
  • 현재 등록부의 구분
    • validation: 자료와 인자가 분석에 맞는 형태인지. 열 사이 중복, 코딩(0/1), 범주 수, 결측 비율, 값 범위
    • preconditions: 추정이 성립할 만큼 자료가 충분한지. 완전사례 행 수, 그룹별 관측 수, 사건 수, 군집 수

표기:

  • 그대로 적은 이름
    • 그 이름의 열이 꼭 있어야 함
    • n처럼 YAML 1.1에서 불리언으로 읽히는 이름은 따옴표로 감쌈(섹션 4.9)
  • <설명>
    • 자료에 따라 이름이 정해지는 열. 그룹 수준이 열 이름이 되는 Table 1이 대표적
    • 꺾쇠 부분은 아무 문자열과 맞음. 이 표기 하나가 열 1개 이상과 대응
    • 현재 쓰이는 예: <그룹 수준>, actual_<비사건 범주>, actual_<사건 범주>, events (<결과변수> = <사건 범주>), mean of <결과변수>, <Overall 또는 그룹 수준>
    • 이름 일부만 자리표시로 둘 수도 있음(예: p(<수준>vs<수준>))
  • A | B
    • 둘(이상) 가운데 하나. 모형 종류에 따라 열 이름이 바뀌는 회귀 결과에 씀
    • 가르는 기호는 세로 막대 앞뒤에 공백을 하나씩 둔 꼴(A | B처럼 씀)
    • 현재 쓰이는 예: OR | Coefficient | RR, log_<효과크기> | <효과크기>
  • 끝의 ?
    • 인자나 자료에 따라 없을 수 있는 조건부 열(예: 신뢰구간을 요청했을 때만 나오는 열)
    • 현재 쓰이는 예: subgroup?, lower 95% CI?, upper 95% CI?, adj. coeff(95%CI)?, adj. P value?, coeff(95%CI)?

판정:

  • 기준은 “필수 열이 모두 있고, 명세에 없는 열이 없는가”
    • wrapper가 디버깅용 열 하나를 더 내거나 열 이름 철자가 한 글자만 달라도 부적합
    • 꺾쇠 표기는 판정에서 정규식 .+로 바뀜 → 열 이름 자체에 <와 >가 함께 들어가면 자리표시로 해석되므로 주의
  • 조건부로 생기는 표(그룹이 있을 때만 나오는 표 등)는 명세에 이름만 적어 두면 됨. 실제 결과에 없어도 부적합으로 보지 않음
  • 반대로 명세에 없는 이름의 표가 결과에 있으면 부적합
  • 그림은 PNG로 저장되고 결과에는 메타데이터만 들어감(섹션 7)
  • figures에 적은 그림은 테스트에서 expect_figure(res, "<이름>")으로 확인

4.5 오류 처리(errors)

errors:
  E_COL_NOT_FOUND: {action: ask_user, message: 데이터에 없는 변수, hint: 유사 변수명을 제안하고 사용자에게 확인}
  E_GROUP_COUNT: {action: ask_user, message: 그룹 범주가 2개가 아님, hint: "3그룹 이상은 JST-TB1-ANOVA를 사용"}
  E_CONSTANT_VARIABLE: {action: block, message: 값이 하나뿐인 변수는 비교할 수 없음, hint: 해당 변수를 제외}
  W_MISSING_HIGH: {action: warn, message: 결측 비율이 20%를 넘음, hint: 완전사례 분석임을 결과 해석에 명시}
  • 키: 오류 코드(E_ 또는 W_로 시작, 대문자·숫자·밑줄)
  • 값: action·message·hint 세 키가 모두 있는 객체
  • action은 block(차단), ask_user(사용자 확인), warn(경고 후 진행) 가운데 하나
  • 접두어와 action 맞추기
    • 코드가 W_로 시작하면 warn, E_로 시작하면 block이나 ask_user
    • 실행 틀은 접두어가 아니라 action만 보고 동작을 정함 → 이 대응은 명세 작성자가 지킴(현재 등록부에서 어긋난 정의는 0개)

명세에 적을 코드:

  • 이 Skill의 규칙이 쓰는 코드 전부
  • 입력 검증에서 나는 공통 코드(E_COL_NOT_FOUND, E_TYPE_MISMATCH, E_INVALID_VALUE 등)도 이 Skill에 맞는 문구로
  • 명세에 없는 공통 코드는 실행 틀의 기본 정의가 쓰임
  • 공통 코드 목록, message·hint가 실제 오류에서 조립되는 방식, action별 agent 동작: 섹션 6
  • 좋은 hint는 사용자가 바로 할 수 있는 일을 적음. 다른 Skill로 가야 하면 그 Skill ID를 적음(위 예의 E_GROUP_COUNT)

4.6 결과 검수 기준(acceptance)

acceptance:
  reference: 변수마다 stats::t.test(x ~ group, var.equal = FALSE)의 p값을 독립 계산
  criterion: "결과표 p값이 기준 p값을 소수 셋째 자리로 반올림한 값과 일치(기준값 < 0.001이면 '<0.001')"
  • reference: 결과값을 기보유 패키지를 거치지 않고 계산하는 방법
    • 기보유 패키지 함수를 다시 불러 같은 값이 나오는지 보는 것은 검증이 아님
    • 기존 명세는 stats·survival 함수를 직접 부르거나 공식을 그대로 계산(예: Pearson 상관의 r, Fisher z 신뢰구간, t 통계량을 공식으로)
  • criterion: 무엇을 몇 자리에서 비교하는지, p값 경계 표기(<0.001)를 어떻게 다루는지, 그림이 있으면 PNG 생성과 해시 일치까지
  • 테스트(섹션 9)는 이 기준을 코드로 옮긴 것이어야 함

  • 아래 표: 2026-10-12에 저장소 라이브러리(.r-lib)의 yaml 2.3.10으로 직접 읽어 확인한 결과
쓴 것 읽힌 값 대처
키 y:, n: 키 이름이 "TRUE", "FALSE"로 바뀜 입력 인자·규칙 키 이름으로 쓰지 않음(입력 이름 y 금지)
키 n:과 no:를 한 매핑에 둘 다 FALSE가 되어 “Duplicate map key” 읽기 오류 같은 이유로 쓰지 않음
목록 값 [variable, n] 두 번째 원소가 논리값 FALSE [variable, "n"]처럼 따옴표
목록 값 yes, on, y / off TRUE / FALSE 따옴표
version: 0.1, 0.10 숫자 0.1 0.1.0처럼 점 두 개(문자열이 됨)
01 정수 1 앞자리 0이 의미 있으면 따옴표

y를 입력 인자 이름으로 쓴 경우:

  • 특히 찾기 어려움. 매핑의 키 y:는 문자열 "TRUE"로, 규칙 목록 안의 값 y는 논리값 TRUE로 읽혀 서로 어긋남
  • 확인 예(2026-10-12): JSM-COR-PEARSON 명세에서 var2를 모두 y로 바꿔 읽음
    • 입력 정의의 이름이 "TRUE"가 됨
    • distinct_columns 규칙의 columns: [var1, y, group]에서는 논리값 TRUE가 인자 목록의 첫 원소(var1)를 가리킴
    • 그 결과 예제 인자로 검증하면 엉뚱하게 E_ARG_CONFLICT(“같은 변수가 중복 지정됨: bili”)로 막힘
    • y라는 이름으로 인자를 넘기면 E_UNKNOWN_PARAM
  • 규칙이 그 인자를 참조하지 않으면 등록부 점검도 잡지 못하고 registry.json에 인자 이름이 "TRUE"로 기록됨(섹션 11의 실패 예시에서 확인)

따옴표가 필요한 문자열:

  • 한 줄 매핑({...}) 안에서 문자열에 [ ] { } , :가 들어가면 YAML 구조로 해석됨 → 따옴표로 감쌈
    • 예: 기존 명세의 message: "var1·var2는 숫자형, group은 범주형이어야 함"은 쉼표 때문에 따옴표를 씀
  • #(공백 뒤 샵)은 주석 시작 → 문자열 안에 쓰려면 역시 따옴표 필요

registry.json의 목록과 값 하나:

  • 등록부 생성기는 schema 검증 때와 같이 YAML 목록을 원소가 하나여도 JSON 배열로 기록
    • 예: figures: [scatter] → "figures": ["scatter"]
  • YAML에 목록이 아니라 값 하나로 쓴 항목은 문자열로 기록
    • r_function·origin은 schema가 문자열과 목록을 모두 허용 → 함수가 하나인 명세는 대개 r_function: jstable::cox2.display처럼 값 하나로 씀
    • 그래서 registry.json을 읽는 코드는 r_function·origin을 문자열과 배열 모두 받아야 함
    • 규칙 키(columns 등)도 columns: group처럼 값 하나로 쓰면 문자열. 규칙은 R 실행 서비스가 YAML을 직접 읽어 쓰므로 실행에는 영향 없음

5 검증 규칙 레퍼런스

5.1 규칙 함수 작성 규약

  • 규칙은 rule_funs 목록에 이름으로 등록된 R 함수
  • 모든 규칙의 시그니처가 같음
rule_funs$<이름> <- function(r, data, p) {
  # r    : 명세의 규칙 객체(list). r[["column"]], r[["min"]] 등
  # data : 데이터셋 전체(data.frame). 완전사례로 줄이지 않은 상태
  # p    : 입력 검증을 통과하고 기본값이 채워진 인자 목록
  # 통과하면 NULL, 위반하면 위반 내용을 설명하는 문자열 하나를 돌려준다
}
rule_required_keys$<이름> <- c("column", "min")   # 명세에 꼭 있어야 하는 키
  • 실행 틀(run_rules())은 규칙이 돌려준 문자열을 오류 메시지 뒤에 붙임
    • 예: n_levels가 "rx의 범주 수 3 (최대 2)"를 돌려주고 명세의 E_GROUP_COUNT 메시지가 “그룹 범주가 2개가 아님”이면 → 사용자가 받는 메시지는 “그룹 범주가 2개가 아님: rx의 범주 수 3 (최대 2)”
  • 경고(warn) 규칙은 "W_MISSING_HIGH: 결측 비율 20% 초과: …"처럼 코드와 내용을 붙여 warnings에 넣음

규칙 함수를 쓸 때 알아 둘 점:

  • 규칙 객체의 열 관련 키는 입력 인자 이름 → 실제 열 이름은 p[[r[["column"]]]]처럼 한 번 더 찾음
    • 여러 인자를 한꺼번에 펼칠 때는 core.R의 param_columns(p, r[["columns"]])를 씀
    • 지정되지 않은 선택 인자는 NULL이라 자연히 빠짐
  • data는 자료 전체
    • 공통 규칙 가운데 min_rows만 지정한 열의 완전사례를 셈. 나머지(n_levels, min_group_size, max_missing_rate 등)는 자료 전체에서 셈
    • 분석은 완전사례로 하는데 완전사례 기준의 사건 수나 쌍 수를 봐야 한다면 계열 전용 규칙을 만듦(예: cor_pairs, km_min_events)
  • 인자는 반드시 r[["키"]], p[["이름"]]으로 읽음
    • $는 부분 일치 → column 키가 없을 때 r$column이 columns를 집어 옴(실제로 겪은 오류. 섹션 8.8)
  • 반환 문자열에 쓰는 값은 정해져 있음(섹션 5.2)
  • 규칙은 데이터를 바꾸지 않음. 판정만 함

5.2 메시지에 쓰는 값

  • 규칙이 돌려준 문자열은 사용자에게 그대로 보이고 LLM에도 전달됨
    • wrapper가 skill_error()에 넣는 상세 문자열도 같음
  • 그래서 데이터셋 구조(GET /datasets/{ref}/schema, 섹션 14)가 내는 것보다 많은 값을 담지 않음
    • 업로드 자료의 데이터셋 구조는 최솟값·최댓값을 내지 않음. 대개 한 사람의 값이기 때문
    • 메시지에 관측 범위를 넣으면 이 제한을 우회하게 됨
    • 공개 데이터셋에도 같은 기준을 씀 → 같은 위반이면 자료 출처와 관계없이 메시지가 같음

담는 것:

  • 변수 이름, 건수, 사용자가 준 인자 값, 규칙 기준값

담지 않는 것:

  • 숫자형 변수의 관측값: 최솟값·최댓값·관측 범위·분위수·개별 행의 값
    • 범위를 벗어난 값은 “관측 범위 밖”처럼 판정만 씀. 실제 범위는 LLM이 데이터셋 구조에서 봄(공개 자료는 최솟값·최댓값, 업로드 자료는 사분위수)
    • 분위수로 정하는 값(예: 스플라인 매듭)이 겹치면 값 대신 겹친 분위수 위치를 씀(예: “5%·27.5% 분위수가 같음”)
  • 대상자 ID, 군집 ID 같은 식별자 값 → 개수만 씀(예: “USUBJID가 2행 이상인 대상자 N명”)

    • 데이터셋 구조에 범주 목록이 나오는 열(숫자형이 아니고 범주 30개 이하)이면 값을 앞에서 n개(기본 5개)까지 붙임
    • 그 밖의 열(숫자형, 범주가 많은 열)이면 빈 문자열 → 호출하는 쪽이 개수를 함께 씀
    • 업로드 자료(up_…)를 실행·검증하는 중이면 데이터셋 구조와 같은 기준을 더함: 날짜·시각 열은 빈 문자열, 관측 수가 5 미만인 범주 값은 뺌

# 데이터셋 구조가 범주 목록을 내는 범주 수 상한(넘으면 개수만 냄)
schema_max_levels <- 30

# 업로드 자료에서 범주 값을 내는 최소 관측 수. 이보다 적은 행에만 있는 값(이름·ID·자유 텍스트처럼 한 사람을
# 가리킬 수 있는 값)은 구조·메시지에 쓰지 않고 개수만 센다. agent의 소표본 셀 기준(PRIVACY_MIN_CELL, 기본 5)과 같다
upload_min_level_n <- function() max(1L, as.integer(Sys.getenv("PRIVACY_MIN_CELL", "5")))

# 열 x의 범주 값을 구조·메시지에 낼 수 있는지(FALSE면 개수만 낸다)
levels_exposable <- function(x, upload = FALSE) {
  !(is.numeric(x) || (upload && inherits(x, c("Date", "POSIXt"))) ||
      length(unique(stats::na.omit(x))) > schema_max_levels)
}

# 범주 값 vals 가운데 낼 수 있는 값. 업로드 자료는 관측 수가 upload_min_level_n() 미만인 값을 뺀다
frequent_levels <- function(x, vals, upload = FALSE) {
  vals <- as.character(vals)
  if (!upload) return(vals)
  cnt <- table(as.character(x))[vals]
  vals[!is.na(cnt) & cnt >= upload_min_level_n()]
}

# 열 x의 범주 값 vals를 메시지에 붙일 문자열(fmt 형식)로 만든다. 데이터셋 구조에 범주 목록이 나오지 않는 열
# (숫자형, 범주가 schema_max_levels개를 넘는 열, 업로드 자료의 날짜·시각)이거나 낼 값이 없으면 빈 문자열을
# 돌려준다(호출 측은 개수를 함께 쓴다).
msg_levels <- function(x, vals, n = 5, fmt = ": %s") {
  upload <- isTRUE(run_context$upload)
  if (!levels_exposable(x, upload)) return("")
  vals <- frequent_levels(x, vals, upload)
  if (length(vals) == 0) return("")
  sprintf(fmt, paste0(paste(utils::head(vals, n), collapse = ", "), if (length(vals) > n) " 등" else ""))
}

5.5 계열 전용 규칙 만들기

  • 새 규칙은 그 규칙을 쓰는 계열 파일(r-executor/R/skills/<계열>.R)에 둠
  • 짧은 예: cor.R의 정규성 경고 규칙
# 정규성(Pearson 상관의 이변량 정규 가정 점검): 두 변수가 모두 있는 관측에서 Shapiro-Wilk p < alpha인 변수가 있으면 위반.
# 표본이 3–5000개일 때만 검정한다
rule_funs$cor_normality <- function(r, data, p) {
  cols <- param_columns(p, r[["columns"]])
  d <- data[stats::complete.cases(data[, cols, drop = FALSE]), cols, drop = FALSE]
  if (nrow(d) < 3 || nrow(d) > 5000) return(NULL)
  pv <- vapply(cols, function(v) if (length(unique(d[[v]])) < 3) NA_real_ else stats::shapiro.test(d[[v]])$p.value, numeric(1))
  low <- pv[!is.na(pv) & pv < r[["alpha"]]]
  if (length(low) > 0) sprintf("Shapiro-Wilk p < %g인 변수: %s", r[["alpha"]], paste(sprintf("%s(p = %.3g)", names(low), low), collapse = ", "))
}

rule_required_keys$cor_normality <- c("columns", "alpha")

만들 때 지킬 것:

  1. 이름에 계열 접두어를 붙임(예: cor_, km_, svy_)
    • 모든 계열 파일이 같은 rule_funs 목록에 규칙을 덧붙임 → 다른 파일과 이름이 같으면 나중에 읽힌 파일이 앞의 정의를 조용히 덮어씀
    • 등록부 생성기가 이 충돌을 “이름 충돌”로 잡지만 처음부터 접두어로 피함
    • 현재 목록에는 접두어 없는 규칙(min_events_per_param, max_factor_levels 등)도 있음. 새 규칙에는 접두어를 붙임
  2. 필수 키를 rule_required_keys에 등록
    • 등록부 생성기가 명세의 규칙 객체에 이 키가 모두 있는지 확인
    • 필수 키가 없는 규칙은 character(0)을 등록(svy.R의 설계 점검 규칙들처럼 Skill 입력 weights·strata·cluster를 직접 읽는 경우)
  3. 선택 키는 NULL을 고려
    • r[["group"]]이 없을 수 있다면 if (!is.null(r[["group"]])) ...로 처리
  4. 규칙 안에서 오래 걸리는 계산을 하지 않음
    • 규칙은 /validate에서도 실행됨. 이 경로는 별도 프로세스·timeout 없이 R 실행 서비스 프로세스에서 돎(섹션 2)
    • 표본이 클 때 검정을 건너뛰는 식으로 상한을 둠(cor_normality는 5,000행을 넘으면 검정하지 않음)
  5. 같은 판정이 정상 사례와 오류 사례 테스트에 모두 드러나게 함
    • 규칙이 위반을 알리는 자료를 테스트에서 하나 이상 만듦(섹션 9)

명세에 거는 법:

  • 규칙을 정의해도 명세에서 쓰지 않으면 아무 일도 하지 않음
  • 명세의 validation이나 preconditions에 {rule: <이름>, ..., error: <코드>}로 걸고 그 코드를 명세 errors에 정의
  • 같은 규칙을 기준값만 바꿔 두 번 걸 수도 있음
    • 예: subgroup Cox 명세는 sg_cell_events를 min: 1과 E_SPARSE_SUBGROUP(차단)으로 한 번, min: 5와 W_FEW_SUBGROUP_EVENTS(경고)로 한 번 걺
    • 효과: 추정이 불가능한 경우는 막고 가능하지만 불안정한 경우는 경고만 함

6.2 공통 오류 코드

  • 실행 틀이 직접 내는 코드와 그 기본 정의(core.R의 default_errors)
  • Skill 명세에 같은 코드를 적으면 명세의 정의가 우선
오류 코드 action 기본 메시지 기본 안내(hint)
E_UNKNOWN_SKILL block 등록되지 않은 Skill 등록부의 Skill ID를 확인
E_UNKNOWN_DATASET block 허용 목록에 없는 데이터셋 등록된 데이터셋만 사용 가능

이 밖에 R 실행 서비스 API 자체가 내는 코드 2개:

  • HTTP 400과 E_BAD_REQUEST: 요청 본문에 skill_id나 dataset_ref가 없음
  • HTTP 409와 E_VERSION_MISMATCH: 요청에 실은 version이 등록된 명세의 버전과 다름
  • 둘 다 Skill 실행 전에 발생 → action과 recovery_hint 없이 code와 message만 있음(섹션 14)

agent 쪽에서 덧붙는 코드:

  • 도구 호출 루프(loop.py)가 만들어 LLM에 돌려줌
    • E_UNKNOWN_TOOL: 등록되지 않은 도구 이름
    • E_TOOL_RUNTIME: 도구 처리 중 Python 예외
    • E_PRIVACY: privacy guard가 결과를 막음
  • 분석계획 API(api.py)는 계획이 막히면 E_PLAN_INVALID로 감싸고 분석별 문제(workflow.py의 check_plan() 결과)를 problems에 담음
  • 이 코드들은 Skill 명세에 적지 않음

wrapper skill_error()로 지정한 코드 반드시 적음. 등록부 점검은 wrapper 안의 코드를 대조하지 않음
wrapper(예상 못 한 오류) E_RUNTIME 적기를 권장. 공통 정의보다 구체적인 hint를 줄 수 있음
timeout E_TIMEOUT 오래 걸릴 수 있는 Skill은 줄일 인자를 hint에 적음
  • E_RUNTIME의 메시지에는 R 오류 메시지가 그대로 들어감(“분석 실행 중 오류: subscript out of bounds” 같은 식)
    • 사용자도 LLM도 이것으로는 무엇을 고칠지 알기 어려움
  • 그래서 예상할 수 있는 실패(사건이 없음, 수렴하지 않음, 그룹이 하나뿐임 등)는 규칙으로 미리 막거나 wrapper 안에서 확인해 구체적인 코드로 바꿈
  fit <- do.call(geepack::geeglm, args)
  if (!identical(as.integer(fit$geese$error), 0L)) {
    stop(skill_error("E_NOT_CONVERGED", sprintf("geepack 반복 추정이 수렴하지 않음(geese error = %s)", fit$geese$error)))
  }
  • 위는 gee.R의 GEE wrapper 일부. 기보유 함수가 수렴 실패를 경고 없이 결과로 내는 문제(섹션 13)를 이렇게 막음
  • skill_error(code, detail, hint)의 세 번째 인자 hint를 주면 명세의 hint 대신 그 문장이 안내로 나감
    • 자료에 따라 안내가 달라질 때 사용(예: meta.R에서 평균의 비(ROM)를 쓸 수 없을 때 “MD 또는 SMD를 사용”)

6.4 action별 동작

  • action은 그 오류를 받은 쪽이 무엇을 해야 하는지 정함
  • ask_user(사용자 확인): 사용자에게 되물으면 풀리는 오류
    • 예: 변수 이름이 틀림, 변수 형식이 맞지 않음, 그룹 수가 이 분석에 맞지 않음
    • 통계실행 agent의 시스템 프롬프트는 이 경우 recovery_hint를 바탕으로 사용자에게 확인 질문을 하라고 지시
    • 인자를 고쳐 다시 시도할 수 있으면 한 번 다시 시도
  • block(차단): 같은 자료로는 이 분석을 할 수 없는 오류
    • 예: 값이 하나뿐인 변수, 사건이 없는 자료, 수렴 실패, timeout
    • agent는 실행할 수 없는 이유와 대안을 설명
  • warn(경고 후 진행): 분석은 할 수 있지만 해석에 주의가 필요한 경우
    • 예: 결측 비율이 높음, 정규성 위반, 희소 칸
    • 실행 틀은 멈추지 않고 "코드: 내용" 문자열을 결과의 warnings에 넣음
    • 이 경고는 LLM에 결과와 함께 전달됨
    • 이어지는 곳: 보고서 문서의 결과 아래 “경고” 줄, 품질 점검의 경고 항목, 데이터 검증의 판정(경고가 있으면 warn)

분석계획 API(POST /projects/{id}/plan):

  • 계획의 분석마다 /validate를 부르고 하나라도 막히면 HTTP 422로 전체를 거부
  • 응답의 problems에 분석 ID와 함께 위 error 객체(code, action, message, recovery_hint)가 그대로 들어감
  • 사용자가 인자를 고쳐 다시 내면 접수됨. 경고만 있는 계획은 접수됨

6.5 timeout

  • timeout은 두 겹
    • R 수준: run_skill()이 wrapper를 부르기 직전에 제한을 걺(R_EXECUTOR_TIMEOUT_SEC, 기본 60초). 넘기면 “실행 시간 제한 초과: 60초 초과” 같은 E_TIMEOUT
    • 프로세스 수준: 컴파일 코드 안에서 멈춰 R 수준 제한이 듣지 않으면 별도 프로세스의 제한(60 + 5초)이 프로세스를 종료. “65초 초과(프로세스 종료)”라는 E_TIMEOUT
  • 두 경우 모두 action은 명세 정의(없으면 block)를 따름
  • 자료 크기나 인자에 따라 오래 걸릴 수 있는 Skill(머신러닝 하이퍼파라미터 탐색, 순열·bootstrap 등)
    • 명세에 E_TIMEOUT을 적고 hint에 줄일 인자를 구체적으로 씀
    • 기존 머신러닝 Skill의 문구: “grid_num·iter·folds를 줄이거나 예측변수 수를 줄여 다시 실행”
  • timeout은 규칙 점검에는 걸리지 않음 → 오래 걸리는 계산을 규칙에 넣지 않음(섹션 5)

6.6 오류 메시지 작성

  • message: 무엇이 문제인지 명사형으로 짧게(예: “그룹 범주가 2개가 아님”)
    • 상세 내용은 규칙·입력 검증이 뒤에 붙임 → 메시지에 열 이름이나 숫자를 넣지 않음
  • 상세 내용(규칙의 반환 문자열, skill_error()의 detail)에는 관측 범위·개별 값·식별자를 넣지 않음(섹션 5.2)
  • hint: 사용자가 바로 할 수 있는 일
    • 다른 Skill로 가야 하면 그 ID(“3그룹 이상은 JST-TB1-ANOVA를 사용”)
    • 자료를 고쳐야 하면 무엇을 어떻게 고칠지(“결측을 확인하거나 그룹 범주를 합치거나 그룹 없이 분석”)
    • 경고의 hint는 결과를 해석할 때 무엇을 적어야 하는지(“완전사례 분석임을 결과 해석에 명시”)
  • 현재 명세에 쓰인 오류 코드 전체와 각 코드를 쓰는 Skill 수: 부록(섹션 16.2)

7.3 JSON 변환 시 주의점

  • R 결과가 JSON이 될 때 몇 가지가 바뀜
  • 결과를 읽는 코드(agent, 시험 실행기, 외부 클라이언트)와 wrapper를 쓰는 사람 모두 알아야 함

바뀌는 것:

  • 길이 1인 벡터는 따로 표시하지 않으면 배열이 아니라 값 하나가 됨
    • notes·warnings는 실행 틀이 I()로 표시해 원소가 하나여도 배열로 냄(core.R의 json_array()). 위 출력의 warnings도 경고 하나짜리 배열
    • 데이터셋 구조(섹션 14)의 levels도 같은 방식으로 범주가 하나여도 배열
    • provenance의 r_function은 명세에 쓴 형태를 따름 → 함수 하나를 값 하나로 쓴 명세는 문자열, 여럿이면 배열. 결과를 읽는 쪽은 둘 다 받게 처리
    • 빈 벡터(character(0))와 빈 목록은 []
  • 2026-10-12 이전의 R 실행 서비스는 notes·warnings가 하나면 문자열로 보냈음
    • agent의 클라이언트(executor.py)는 둘 다 목록으로 맞춰 받음
    • 그 무렵 저장된 결과를 읽는 보고서·품질검증도 문자열을 한 항목으로 다룸
  • 숫자는 소수 넷째 자리까지만 나감
    • jsonlite::toJSON()의 기본 자릿수(digits = 4)를 그대로 쓰기 때문. 0.123456은 0.1235가 됨
    • 결과표의 숫자는 wrapper에서 보고할 자릿수로 반올림해 둠
    • p값처럼 경계 표기(<0.001)가 필요한 값은 문자열로 만듦
    • 예: 상관 계열 wrapper는 r·신뢰구간·t를 소수 셋째 자리로 반올림하고 p값은 문자열로 냄
  • NA는 null이 됨
    • 결측 칸이 있는 표도 행마다 열 집합이 같게 유지됨
    • 시험 실행기는 행마다 열이 다르면 부적합으로 봄
  • 행 이름은 사라짐
    • data.frame의 행 이름은 JSON에 들어가지 않음 → 변수 이름처럼 의미 있는 행 이름은 matrix_to_df() 등으로 열로 옮김(섹션 8)

7.4 그림

  • wrapper가 save_figure()로 저장한 그림은 PNG 파일로 남음
    • 파일 이름: 내용의 SHA-256 해시에 .png를 붙인 것
    • 저장 위치: R_EXECUTOR_FIGURE_DIR. 설정되지 않았으면 R 임시 폴더 아래 figures
    • R 실행 서비스는 기동할 때 이 폴더를 정해 별도 실행 프로세스에도 넘김
  • 클라이언트는 결과의 file로 GET /figures/<file>을 불러 PNG를 받음
    • API는 64자리 16진수 + .png 형식이 아닌 이름을 400으로 거부
  • agent의 분석계획 실행(run-plan)
    • 결과의 그림마다 이 API로 PNG를 받아 프로젝트 산출물로 저장하고 결과에 산출물 ID를 붙임
    • LLM에는 그림의 name과 title만 전달됨
  • 그림에 표시한 수치는 반드시 표로도 냄
    • LLM은 그림을 보지 못하고 표만 인용
    • 보고서의 수치 검증도 표가 기준

8 wrapper 작성 규칙

8.1 시그니처와 반환 구조

  • wrapper는 인자 두 개를 받는 함수
skill_<계열>_<방법> <- function(data, p) {
  # data : 데이터셋 전체(data.frame). 허용 목록의 loader()가 만든 그대로
  # p    : 입력 검증과 규칙 점검을 통과한 인자 목록. 빠진 선택 인자에는 명세의 default가 채워져 있다
  list(
    tables   = list(<표 이름> = <data.frame>, ...),   # 필수. 이름은 명세 outputs.tables와 같게
    figures  = list(save_figure(...), ...),            # 선택. 이름은 명세 outputs.figures와 같게
    notes    = c("사용한 검정: ...", ...),              # 선택. 한국어
    warnings = c("W_코드: 내용", ...)                   # 선택
  )
}
  • wrapper가 불릴 때는 이미 열 이름, 형식, 범위, 규칙 점검이 끝난 상태
    • 같은 검사를 반복하지 않고 분석에 집중
    • 단 완전사례로 줄인 뒤에야 알 수 있는 문제(사건이 하나도 남지 않음, 그룹이 하나만 남음 등)는 wrapper가 확인하고 skill_error()로 막음(섹션 6)
  • p에 없는 선택 인자는 p[["이름"]]이 NULL → if (!is.null(p[["group"]]))처럼 분기
  • 아래는 가장 단순한 wrapper인 JST-TB1-TTEST의 실행 경로 전체를 tb1.R에서 옮긴 것
    • 계열 공통 도우미 세 개(tb1_prepare, tb1_run, tb1_output)와 Skill 함수 하나로 구성
# 분석에 필요한 열만 남기고 범주형 변수를 factor로 맞춘다.
# (jstable의 normalityTest는 data의 모든 숫자형 열을 검정하므로 열을 줄여서 넘겨야 한다)
# factor_vars를 주지 않으면 숫자형이 아닌 변수만 범주형으로 본다.
tb1_prepare <- function(data, vars, groups = NULL, factor_vars = NULL) {
  d <- data[, unique(c(vars, groups)), drop = FALSE]
  for (g in groups) d[[g]] <- droplevels(factor(d[[g]]))
  if (is.null(factor_vars)) factor_vars <- vars[!vapply(vars, function(v) is.numeric(d[[v]]), logical(1))]
  for (v in factor_vars) d[[v]] <- droplevels(factor(d[[v]]))
  list(data = d, factor_vars = if (length(factor_vars) > 0) factor_vars else NULL)
}

tb1_run <- function(data, vars, group = NULL, ..., factor_vars = NULL) {
  prep <- tb1_prepare(data, vars, group, factor_vars)
  args <- list(vars = vars, data = prep$data, factorVars = prep$factor_vars,
               showAllLevels = TRUE, printToggle = FALSE, ...)
  if (!is.null(group)) args$strata <- group
  res <- do.call(jstable::CreateTableOneJS, args)
  df <- matrix_to_df(res$table)
  df$sig <- NULL
  list(table = df, caption = res$caption)
}

tb1_output <- function(run, notes = character()) {
  list(tables = list(table1 = run$table), notes = c(run$caption, notes))
}

# 연속변수 2그룹 비교: Welch t-test
skill_tb1_ttest <- function(data, p) {
  run <- tb1_run(data, p$vars, p$group, test = TRUE, nonnormal = NULL)
  tb1_output(run, "p값: Welch two-sample t-test (oneway.test, var.equal = FALSE)")
}

이 코드에 이 장의 규칙 대부분이 들어 있음:

  • 필요한 열만 잘라서 넘김(tb1_prepare)
  • 그룹 변수를 factor로 맞춤
  • 기보유 함수의 행렬 출력을 matrix_to_df()로 표로 바꿈
  • 사용한 검정을 notes에 적음

8.2 자료 준비

  • 필요한 열만 넘김
    • 기보유 함수 가운데는 넘겨받은 자료의 모든 열을 처리하는 것이 있음
    • 예: jstable::CreateTableOneJS(normalityTest = TRUE)는 data의 모든 숫자형 열에 정규성 검정을 함 → 분석과 무관한 상수 열이 하나만 있어도 실패(섹션 13)
    • 그래서 wrapper는 분석에 쓰는 열만 남긴 자료를 넘김
  • 완전사례와 형식 변환은 wrapper에서 명시적으로 함
    • 범주형으로 쓸 변수는 droplevels(factor(x))로 바꿈
    • 결측 행을 뺄 때는 어떤 열 기준인지 분명히 함
    • 기보유 함수가 내부에서 결측을 다르게 처리하면(예: 단변량과 다변량 모형의 표본이 달라지는 경우) 결과의 의미가 바뀜 → 모형 변수의 완전사례만 넘기는 식으로 표본을 고정
    • 실제로 쓴 표본 수를 notes에 적음(예: “bili·albumin·sex에 결측이 없는 312쌍 사용”)
  • 자료를 고치지 않음
    • data는 그 실행에서만 쓰는 사본이지만 전역 환경이나 다른 객체를 바꾸지 않음
    • 파일은 save_figure() 말고는 쓰지 않음
    • 네트워크에 접근하지 않음

8.3 결과표

  • 집계값만 담음
    • 넣는 것: 요약통계, 검정 통계량, 추정치, 건수
    • 넣지 않는 것: 개인 단위의 값(행 단위 자료, 개별 예측값, 잔차 목록 등). 결과표는 LLM과 보고서로 가기 때문
    • agent의 privacy guard는 결과표 하나가 200행을 넘으면 행 단위 자료가 섞였을 수 있다고 보고 LLM에 넘기지 않음(E_PRIVACY)
    • 시점별 생존율처럼 행이 많아질 수 있는 표는 시점 간격 인자로 행 수를 제한
  • 건수 열의 이름을 알아보기 쉽게 지음
    • 업로드 자료(up_*)로 실행한 결과는 LLM에 넘기기 전에 소표본 셀(1 ~ k−1건, 기본 k = 5)을 <5로 가림
    • 건수로 알아보는 기준: 열 이름이 n, count, freq, events, n_event, n.risk, cases, 건수, 빈도 같은 이름인지, 셀이 12 (34.5) 꼴의 빈도(백분율)인지
    • Table 1의 variable이 n인 행은 행 전체를 건수로 봄
    • 건수를 담는 열에 다른 이름을 붙이면 가려지지 않음
  • 기보유 함수의 행렬 출력은 matrix_to_df()로 바꿈
    • jstable과 tableone이 돌려주는 문자 행렬은 행 이름에 변수 이름이 있고 범주 수준 행은 행 이름이 비어 있음
    • matrix_to_df()는 비어 있는 행 이름을 바로 위 변수 이름으로 채워 variable 열로 옮김
    • 모든 셀을 공백을 다듬은 문자열로 바꾸고 NA를 빈 문자열로 바꿈
# jstable/tableone이 돌려주는 문자 행렬을 data.frame으로 바꾼다.
# 행 이름(변수명)이 비어 있는 행은 직전 변수의 하위 범주이므로 변수명을 채운다.
matrix_to_df <- function(m, row_col = "variable") {
  m <- as.matrix(m)
  rn <- rownames(m) %||% rep("", nrow(m))
  rn <- trimws(rn)
  for (i in seq_along(rn)) if (i > 1 && !nzchar(rn[i])) rn[i] <- rn[i - 1]
  df <- as.data.frame(m, stringsAsFactors = FALSE, check.names = FALSE)
  df[] <- lapply(df, function(x) { x <- trimws(as.character(x)); x[is.na(x)] <- ""; x })
  df <- cbind(stats::setNames(data.frame(rn, stringsAsFactors = FALSE), row_col), df)
  rownames(df) <- NULL
  df
}
  • 열 이름과 표 이름은 명세와 똑같이
    • 시험 실행기는 열 이름을 문자 그대로 대조(섹션 4.4)
    • 기보유 함수가 버전이나 옵션에 따라 다른 열 이름을 내면 wrapper에서 이름을 고정
    • 기보유 함수가 디버깅용·내부용 열(jstable의 sig 같은)을 붙이면 지움
  • 숫자는 보고 자릿수로 반올림
    • JSON으로 나갈 때 소수 넷째 자리에서 잘림(섹션 7) → 표의 숫자는 wrapper에서 의도한 자릿수로 반올림
    • p값은 "<0.001" 경계 표기를 위해 문자열로 만듦
    • 표기 규칙(소수 셋째 자리, 0.001 미만은 <0.001 등)을 notes에 적음

  • 그림은 save_figure()로 저장하고 그 반환값을 figures 목록에 넣음
save_figure <- function(plot, name, title, width = 7, height = 5, dpi = 150) {
  dir <- figure_dir()
  tmp <- tempfile(fileext = ".png", tmpdir = dir)
  ragg::agg_png(tmp, width = width, height = height, units = "in", res = dpi)
  tryCatch({
    if (inherits(plot, c("gtable", "grob", "gTree"))) grid::grid.draw(plot) else print(plot)
  }, finally = grDevices::dev.off())
  hash <- digest::digest(file = tmp, algo = "sha256")
  final <- file.path(dir, paste0(hash, ".png"))
  file.rename(tmp, final)
  list(name = name, title = title, format = "png", file = basename(final), sha256 = hash,
       width_in = width, height_in = height, dpi = dpi)
}
  • ggplot 객체와 grid 객체(gtable, grob, gTree) 모두 받음
  • ragg로 PNG를 그린 뒤 내용 해시를 파일 이름으로 바꿈 → 같은 그림이면 같은 파일 이름
  • name은 명세 outputs.figures의 이름과 같게, title은 사람이 읽는 제목(한국어 가능)으로
  • 그림 안의 문구(축 이름, 범례, 라벨)는 영문
    • 실행 환경에 한글 글꼴이 없을 수 있음
    • 해설은 표와 notes에 한국어로
  • 그림에 표시한 수치(중앙생존시간, log-rank p, AUC, 상관계수 등)는 같은 계산으로 표에도 냄. LLM은 그림을 보지 못함
  • 그림을 그리는 함수가 예상된 경고(예: 쌍별 결측 제외로 “Removed n rows”)를 내면 그 경고만 골라 흡수할 수 있음(cor.R의 skill_cor_matrix() 참고)
    • 나머지 경고는 실행 틀이 모음

8.6 난수 시드

  • 순열 검정, bootstrap, Monte Carlo, cross-validation처럼 난수를 쓰는 분석은 같은 입력에서 같은 결과가 나와야 함
    • 품질 점검이 같은 분석을 다시 실행해 결과표가 같은지 비교하기 때문
  • core.R의 with_seed()로 고정 시드에서 실행 → 실행 전의 전역 난수 상태가 복원됨
# 난수를 쓰는 분석(순열·부트스트랩·몬테카를로)은 고정 시드로 실행하고 호출 전 난수 상태를 되돌린다.
# 같은 입력이면 같은 결과가 나와야 재현성 점검(품질검증)과 일관성 지표가 성립한다.
with_seed <- function(seed, expr) {
  had <- exists(".Random.seed", envir = globalenv(), inherits = FALSE)
  old <- if (had) get(".Random.seed", envir = globalenv()) else NULL
  on.exit({
    if (had) assign(".Random.seed", old, envir = globalenv())
    else if (exists(".Random.seed", envir = globalenv(), inherits = FALSE)) rm(".Random.seed", envir = globalenv())
  }, add = TRUE)
  set.seed(seed)
  expr
}
  • 시드를 정하는 두 가지 방식
    • 사용자가 바꿀 수 있게 하려면 seed 입력 인자(type: integer, default, min: 1)를 둠
    • 그렇지 않으면 wrapper 안의 상수로 고정
    • 어느 쪽이든 쓴 시드를 notes에 적음
  • 기존 계열의 예
    • km.R의 km_with_seed(): 난수 생성기 종류(kind = "Mersenne-Twister", normal.kind = "Inversion", sample.kind = "Rejection")까지 고정
    • ps.R의 ps_with_seed(): 상수 시드
  • 기보유 함수가 내부에서 시드를 다시 고정해 사용자 시드가 결과에 영향을 주지 않는 경우도 있음(ml.R의 K-평균 군집 주석 참고) → 시드 인자를 두기 전에 실제로 결과가 바뀌는지 확인

8.7 formula 만들기

  • 사용자 입력으로 모형식을 만들 때 문자열을 이어 붙여 eval(parse())하지 않음
  • 열 이름은 입력 검증에서 R 문법에 맞는 이름만 통과(섹션 4.2) → stats::reformulate()에 문자 벡터로 넘기면 됨
  • Surv()처럼 함수 호출이 응답변수가 되는 경우에는 as.name()과 as.call()로 호출 객체를 만듦. cox.R의 방식:
# survival::Surv(time, event) 호출
cox_surv <- function(time, event) as.call(list(quote(survival::Surv), as.name(time), as.name(event)))

# coxph 적합. data_sym은 데이터 symbol(기본은 이 함수의 d), extra_args는 cluster·id 등 추가 인자
cox_fit <- function(d, p, terms, extra_args = list(), data_sym = quote(d)) {
  env <- environment()
  f <- stats::reformulate(terms, response = cox_surv(p$time, p$event))
  cl <- as.call(c(list(quote(survival::coxph), formula = f, data = data_sym, model = TRUE), extra_args))
  eval(cl, envir = env)
}
  • 기보유 함수가 적합 객체의 call을 다시 평가하는 경우(crude 모형 재적합 등)
    • 데이터와 모형식이 call 안에 기호나 값으로 제대로 박혀 있어야 함
    • 위의 cox_fit()처럼 as.call()로 호출을 만들어 평가하거나 do.call()에 값을 넘김
    • 어떤 방식이 맞는지는 기보유 함수의 코드를 읽고 정함

8.8 [[ ]]로 읽기

  • 규칙 함수와 wrapper에서 인자는 r[["column"]], p[["center"]]처럼 [[ ]]로 읽음
  • R의 $는 목록에서 이름이 정확히 일치하는 원소가 없으면 부분 일치하는 원소를 돌려줌
    • column 키가 없을 때 r$column은 columns를 집어 옴
    • center 인자가 없을 때 p$center는 centered를 집어 옴
    • 두 경우 모두 실제로 겪은 오류
  • 기존 코드에는 p$vars처럼 $를 쓴 곳이 남아 있음
    • 그 인자 이름이 다른 인자 이름의 앞부분이 되지 않는 경우에만 안전
    • 예: 인자 group과 group2를 함께 두고 group을 선택 인자로 하면 group을 주지 않았을 때 p$group이 group2의 값을 돌려줌
  • 새 코드에서는 [[ ]]만 씀

8.9 전역 객체를 피할 수 없을 때

  • 일부 기보유 함수는 적합 객체의 call에 적힌 데이터 이름으로 전역 환경에서 자료를 다시 찾음
    • 함수 안에서 적합한 모형을 넘기면 실패
    • 같은 이름의 다른 전역 객체가 있으면 그것으로 조용히 틀린 값을 계산(섹션 13의 A1)

    • 이미 그 이름이 있으면 멈춤
    • 끝나면 반드시 지움
cox_with_global_data <- function(d, fn) {

  • 데이터셋을 경로로 읽기. 데이터는 data 인자로만 받음

9.1 테스트 대상

  1. 정상 사례 1개 이상

expect_skill_error <- function(res, code) {
  expect_equal(res$status, "error")
  expect_equal(res$error$code, code, info = res$error$message)

}

# 그림 결과 확인: 메타데이터가 있고, 파일이 실제 PNG이며 내용 해시가 파일 이름과 같음
expect_figure <- function(res, name) {
  figs <- Filter(function(f) identical(f$name, name), res$figures)
  expect_length(figs, 1)
  f <- figs[[1]]
  path <- file.path(figure_dir(), f$file)
  expect_true(file.exists(path))
  expect_equal(readBin(path, "raw", 8), as.raw(c(0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a)))
  expect_gt(file.info(path)$size, 2000)
  expect_equal(digest::digest(file = path, algo = "sha256"), f$sha256)
  invisible(f)
}

9.3 기준값 대조 요령

  • 같은 자료를 같은 방식으로 줄임
    • 기준값 계산도 resolve_dataset()으로 같은 전처리를 거친 자료에서 시작
    • Skill이 쓰는 완전사례 기준(어떤 열에 결측이 없는 행인지)을 그대로 따름
    • 예: JSM-COR-PEARSON 테스트는 complete.cases(d[, c("bili", "albumin", "sex")])로 줄인 뒤 그룹별로 나눔
  • 표시 자릿수로 비교
    • 결과표가 소수 셋째 자리로 반올림한 값이면 기준값도 round(x, 3)으로 반올림해 expect_equal()로 비교
    • 허용오차로 느슨하게 비교하지 않음
    • p값은 fmt_p()로 같은 문자열을 만듦
  • 기보유 함수가 틀리는 경우를 사례에 넣음
    • wrapper가 기보유 함수의 버그를 우회했다면(섹션 13) 우회하지 않았을 때 값이 달라지는 자료를 정상 사례에 넣음 → 우회가 계속 유지되는지 고정
    • 예: subgroup Cox 명세의 검수 기준에 “노출 변수명이 공변량 이름 안에 들어 있어도 기준값과 일치”가 들어 있음
  • 건수와 자유도도 비교
    • p값만 맞고 표본 수가 다르면 다른 분석
    • n, df, 사건 수처럼 정수인 값은 정확히 일치해야 함
  • provenance 한 가지는 확인해 둠
    • JST-TB1-TTEST 테스트처럼 res$provenance$r_function을 확인하면 명세와 wrapper가 이어져 있는지 함께 봄
  • 테스트는 난수나 네트워크에 의존하지 않게 씀
    • 난수를 쓰는 Skill은 시드를 고정했으므로(섹션 8) 같은 인자로 두 번 실행해 결과표가 같은지 확인하는 사례를 넣어도 좋음

# 변수 쌍(columns가 3개 이상이면 모든 쌍)마다 둘 다 결측이 없는 관측 수 하한.
# group 키(입력 인자 이름)의 값이 있으면 그룹 수준별로도 점검하고, 그룹 안에서 값이 하나뿐인 변수도 위반으로 본다
rule_funs$cor_pairs <- function(r, data, p) {
  cols <- param_columns(p, r[["columns"]])
  grp <- if (!is.null(r[["group"]])) p[[r[["group"]]]]
  if (length(cols) < 2) return(NULL)
  pairs <- utils::combn(cols, 2, simplify = FALSE)
  bad <- character()
  for (pr in pairs) {
    d <- data[stats::complete.cases(data[, c(pr, grp), drop = FALSE]), c(pr, grp), drop = FALSE]
    if (nrow(d) < r[["min"]]) bad <- c(bad, sprintf("%s–%s 전체 %d쌍", pr[1], pr[2], nrow(d)))
    if (!is.null(grp)) {
      for (g in sort(unique(as.character(d[[grp]])))) {
        dg <- d[as.character(d[[grp]]) == g, , drop = FALSE]
        const <- any(vapply(pr, function(v) length(unique(dg[[v]])) < 2, logical(1)))
        if (nrow(dg) < r[["min"]] || const) {
          bad <- c(bad, sprintf("%s–%s %s=%s %d쌍%s", pr[1], pr[2], grp, g, nrow(dg), if (const) "(값이 하나뿐인 변수)" else ""))
        }
      }
    }
  }
  if (length(bad) > 0) sprintf("결측 없는 쌍이 %d개 미만이거나 값이 하나뿐: %s", r[["min"]], paste(utils::head(bad, 3), collapse = "; "))
}

  out$notes <- c("Pearson 적률상관계수 r, 95% CI는 Fisher z 변환, p는 t = r·sqrt((n-2)/(1-r²)) 자유도 n-2 검정(stats::cor.test)",
                 "선형 관계만 잰다. 이상치에 민감하며 치우친 분포·순서형 자료는 JSM-COR-SPEARMAN 사용", out$notes)

cor_skill <- function(data, p, method) {
  d <- cor_prepare(data, c(p$var1, p$var2), p$group)
  tab <- cor_table(d, p$var1, p$var2, p$group, method)
  plt <- cor_scatter(d, p, method)
  label <- if (method == "pearson") "Pearson" else "Spearman"
  fig <- save_figure(plt, "scatter", sprintf("%s–%s 산점도와 %s 상관계수", p$var1, p$var2, label), width = 6.5, height = 5.5)
  list(tables = list(correlation = tab), figures = list(fig), notes = c(
    sprintf("%s·%s%s에 결측이 없는 %d쌍 사용. 그룹을 지정하면 전체와 그룹별 상관을 함께 제시", p$var1, p$var2,
            if (is.null(p$group)) "" else paste0("·", p$group), nrow(d)),
    cor_line_note(p$line),
    "p값 표기: 소수 셋째 자리, 0.001 미만은 <0.001. 그림 라벨의 계수는 유효숫자 2자리"
  ))
}

cor_prepare <- function(data, cols, group = NULL) {
  d <- data[, unique(c(cols, group)), drop = FALSE]
  d <- d[stats::complete.cases(d), , drop = FALSE]
  if (!is.null(group)) d[[group]] <- droplevels(factor(d[[group]]))
  rownames(d) <- NULL
  d
}

# 전체와 그룹 수준별 상관 표
cor_table <- function(d, v1, v2, group, method) {
  sets <- c(list(`전체` = d), if (!is.null(group)) split(d, d[[group]]))
  rows <- lapply(names(sets), function(g) {
    x <- sets[[g]][[v1]]
    y <- sets[[g]][[v2]]
    ct <- suppressWarnings(stats::cor.test(x, y, method = method))
    if (method == "pearson") {
      data.frame(group = g, n = length(x), r = round(unname(ct$estimate), 3),
                 CI_low = round(ct$conf.int[1], 3), CI_high = round(ct$conf.int[2], 3),
                 t = round(unname(ct$statistic), 3), df = unname(ct$parameter), p = cor_fmt_p(ct$p.value),
                 stringsAsFactors = FALSE)
    } else {
      data.frame(group = g, n = length(x), rho = round(unname(ct$estimate), 3), S = round(unname(ct$statistic), 1),
                 p = cor_fmt_p(ct$p.value), p_method = cor_spearman_p_method(x, y), stringsAsFactors = FALSE)
    }
  })
  out <- do.call(rbind, rows)
  out$variable1 <- v1
  out$variable2 <- v2
  out[, c("variable1", "variable2", setdiff(names(out), c("variable1", "variable2")))]
}

cor_fmt_p <- function(x) ifelse(is.na(x), "", ifelse(x < 0.001, "<0.001", sprintf("%.3f", round(x, 3))))
  • cor_prepare(): 필요한 열만 남기고 완전사례로 줄이며 그룹을 factor로 맞춤
  • cor_table()
    • 전체와 그룹 수준별로 stats::cor.test()를 부름
    • 통계량을 소수 셋째 자리로 반올림하고 p값을 cor_fmt_p()로 문자열로 만듦
    • 열 순서는 명세의 columns와 같음
  • cor_skill()
    • 산점도를 save_figure()로 저장(이름 scatter)
    • 사용한 쌍 수와 추세선, p값 표기 규칙을 notes에 적음
    • 그림 라벨은 영문
  • skill_cor_pearson(): 계산 방법과 해석상 주의를 notes 앞에 덧붙임

# JSM-COR-PEARSON: 기준값은 Pearson 공식으로 직접 계산하고 stats::cor.test와도 대조(jsmodule·ggpubr를 거치지 않음)

pearson_ref <- function(x, y) {
  n <- length(x)
  r <- sum((x - mean(x)) * (y - mean(y))) / sqrt(sum((x - mean(x))^2) * sum((y - mean(y))^2))
  ci <- tanh(atanh(r) + c(-1, 1) * qnorm(0.975) / sqrt(n - 3))
  t <- r * sqrt((n - 2) / (1 - r^2))
  list(n = n, r = r, ci = ci, t = t, p = 2 * pt(-abs(t), n - 2))
}

test_that("JSM-COR-PEARSON 정상: 전체·그룹별 r·Fisher z CI·t·p가 공식 계산과 일치", {
  res <- run("JSM-COR-PEARSON", "pbc", list(var1 = "bili", var2 = "albumin", group = "sex"))
  expect_skill_ok(res)
  tab <- res$tables$correlation
  d <- resolve_dataset("pbc")
  d <- d[complete.cases(d[, c("bili", "albumin", "sex")]), ]
  sets <- c(list(`전체` = d), split(d, d$sex))
  expect_equal(tab$group, names(sets))
  for (g in names(sets)) {
    ref <- pearson_ref(sets[[g]]$bili, sets[[g]]$albumin)
    i <- tab$group == g
    expect_equal(tab$n[i], ref$n, info = g)
    expect_equal(tab$df[i], ref$n - 2, info = g)
    expect_equal(tab$r[i], round(ref$r, 3), info = g)
    expect_equal(c(tab$CI_low[i], tab$CI_high[i]), round(ref$ci, 3), info = g)
    expect_equal(tab$t[i], round(ref$t, 3), info = g)
    expect_equal(tab$p[i], fmt_p(ref$p), info = g)
    expect_equal(tab$p[i], fmt_p(cor.test(sets[[g]]$bili, sets[[g]]$albumin)$p.value), info = g)
  }
  # 빌리루빈은 심하게 치우친 분포 → 정규성 경고
  expect_true(any(startsWith(res$warnings, "W_NONNORMAL")))
  expect_figure(res, "scatter")
})

12.4 실행 기록(provenance)

  • 모든 결과에는 provenance(섹션 7)가 붙음
    • 남는 것: Skill ID·버전, 연결 R 함수, 데이터셋, 인자 해시, R 버전, 고정 패키지 목록의 설치 버전(GitHub 패키지는 커밋 SHA 앞 7자리 포함), 실행 시각
    • agent는 이것을 Audit Trail과 trajectory에 저장
  • 등록부의 registry.xlsx ‘생성 정보’ 시트와 REGISTRY.md 머리에도 등록부를 만들 때의 R 버전과 패키지 버전이 기록됨
  • 결과 자체의 재현성은 wrapper가 책임짐
    • 난수를 쓰는 계산은 시드를 고정(섹션 8)
    • 자료 전처리는 데이터셋 loader()에 모두 적음
  • 품질 점검 기능은 실행한 분석을 같은 인자로 한 번 더 실행해 결과표가 같은지 비교 → 재현되지 않는 Skill은 여기서 드러남

13.1 대응 원칙

  1. 결과가 틀리는 동작(A 등급)은 wrapper에서 고치고 테스트로 고정
    • 고친 결과는 기보유 패키지를 거치지 않은 독립 기준값과 대조
    • 버그가 드러나는 자료를 정상 사례에 넣어 두면 나중에 누가 우회 코드를 지워도 테스트가 실패
  2. 실패하는 조건(B 등급)은 규칙으로 미리 막거나 실패하지 않는 호출 방식으로 바꿈
    • 사용자는 알 수 없는 R 오류(E_RUNTIME) 대신 이유와 대안이 있는 오류를 받아야 함
  3. 표기 문제(C 등급)는 결과표에서 바로잡고 바로잡은 사실을 notes에 적음
  4. 우회 방법은 계열 파일 머리말 주석에 적음
    • 적을 것: 기준 버전에서 직접 실행해 확인한 동작, 재현 자료, 대응
    • 적어 두면 다음 사람이 같은 함수를 쓸 때 다시 조사하지 않아도 됨(tb1.R, cox.R, km.R, cor.R 머리말 참고)
  5. 고칠 수 없으면 그 기능을 Skill에 넣지 않음
    • 예: jsmodule의 ROC 모듈은 서베이·GEE 모형에서도 가중치와 군집을 무시하고 ROC를 계산 → 서베이·GEE ROC 변형은 만들지 않음

  • 중복 검정을 끄면 실패하는 Table 1(B1)

# jstable 1.3.25 CreateTableOneJS는 strata를 주고 test = FALSE로 부르면
# "subscript out of bounds"로 실패한다(mtcars로 재현됨). 검정을 켜서 실행한 뒤 p·test 열을 지운다.
tb1_run_without_test <- function(data, vars, group = NULL, ...) {
  if (is.null(group)) return(tb1_run(data, vars, NULL, test = FALSE, ...))
  run <- tb1_run(data, vars, group, test = TRUE, ...)
  run$table <- run$table[, setdiff(names(run$table), c("p", "test")), drop = FALSE]
  run
}
  • 전역 자료를 이름으로 다시 찾는 표 함수(A1)
    • coxme.display와 다중상태 cox2.display는 단변량(crude) 모형을 다시 적합할 때 적합 객체의 call에 적힌 데이터 이름으로 자료를 찾음
    • 함수 안에서 적합한 모형을 넘기면 실패
    • 같은 이름의 전역 객체가 있으면 그 자료로 crude 값을 조용히 계산(lung 자료 혼합효과 Cox의 ph.ecog crude 값이 1.66이어야 하는데 1.96으로 나온 사례)
    • wrapper는 고정된 임시 이름으로 전역에 자료를 두고 끝나면 지움(섹션 8의 cox_with_global_data())
    • 이 때문에 R 실행 서비스는 요청을 하나씩 처리
  • 변수 이름 부분 일치로 틀린 interaction p값(A2)
    • subgroup 표 함수는 interaction 모형식을 문자열 치환(gsub)으로 만듦
    • 노출 변수 이름이 다른 변수 이름의 일부이면(노출 rx, 공변량 agerx) 엉뚱한 항이 바뀌어 다른 interaction의 p값(0.259, 정답 0.055)이 나옴
    • wrapper는 노출 변수를 자료의 어떤 이름과도 겹치지 않는 내부 이름으로 복사해 실행하고 결과의 이름을 원래대로 되돌림
# 분석 자료를 만들고 노출 변수를 내부 이름으로 옮긴다(jstable 교호작용 gsub 버그 회피).
# 내부 이름은 자료의 어떤 변수명에도 들어 있지 않은 이름이라 gsub가 노출 항만 바꾼다
sub_prepare <- function(data, p, cols, binary_outcome = NULL) {
  d <- rm_prepare(data, cols, binary_outcome = binary_outcome)
  for (v in c(p$exposure, p$subgroups)) d[[v]] <- droplevels(factor(d[[v]]))
  tmp <- "sgexposure"
  while (any(grepl(tmp, c(names(d), "survival", "Surv"), fixed = TRUE))) tmp <- paste0(tmp, "x")
  d[[tmp]] <- d[[p$exposure]]
  d[[p$exposure]] <- NULL
  list(data = d, exposure = tmp)
}

    • 하나의 규칙으로 차단 기준과 경고 기준을 나눠 두는 방식은 다른 Skill에도 쓸 수 있음
  • 수렴 실패를 조용히 결과로 내는 GEE 표(A10)

    • 같은 함수는 자료가 군집 ID로 정렬되지 않으면 군집을 잘못 나누면서 표의 군집 수는 원래 값으로 보여 줌(A9) → wrapper는 적합 전에 ID(와 시간) 순으로 정렬
  • 고정된 1.96(A13)

    • 이처럼 “틀린 것은 아니지만 관례와 다른” 동작은 명세와 notes에 드러내는 쪽을 택함

14.3 조회 endpoint

  • GET /health
    • {"status": "ok", "skills": <등록 Skill 수>, "packages": {…}}를 돌려줌
    • packages는 provenance와 같은 패키지 버전 목록
    • 위의 로컬 실행에서는 skills가 106
  • GET /skills
    • 등록 Skill마다 id, name, method, category, description, version, inputs를 담은 배열을 돌려줌
    • 규칙·오류·출력 정의는 담지 않음
    • agent는 이 endpoint가 아니라 registry.json으로 도구를 만듦
  • GET /datasets/{ref}/schema: 데이터셋 구조를 돌려줌
    • 최상위: dataset, source, description, n_rows와 변수 목록 variables
    • 변수마다 name, class, n_missing. 숫자형이면 요약통계(summary: min, q1, median, q3, max, mean)와 서로 다른 값 수(n_unique), 범주형이면 수준 목록(levels, 범주가 하나여도 배열. 30개를 넘으면 개수 n_levels만)
    • 행 단위 값은 없음. 업로드 자료는 최솟값·최댓값을 빼고, 5행 미만에만 있는 범주는 levels에서 빼고 그 개수를 n_rare_levels로, 날짜·시각 열은 개수 n_levels만 줌
    • agent는 이것을 LLM에 데이터셋 구조로 넘김 → 데이터셋 description과 범주 수준 이름이 LLM이 자료를 이해하는 근거
    • 허용 목록에 없는 ID는 404
  • GET /figures/{file}: Skill이 저장한 그림 PNG를 돌려줌(Content-Type: image/png)
    • file이 64자리 16진수 + .png 형식이 아니면 400, 파일이 없으면 404
    • 위 로컬 실행에서 JSM-COR-PEARSON 결과의 file로 받은 PNG의 SHA-256은 결과 메타데이터의 sha256과 같았음

15.1 실행과 출력 형식 판정

  • 실행기는 명세의 예제(examples)마다 그 인자로 분석계획을 제출하고 실행한 뒤 결과 JSON을 받아 아래를 확인
확인 항목 기준
실행 성공 결과의 status가 ok이고 error가 없음
표 형식 결과의 표 이름이 모두 명세 outputs.tables에 있음. 표마다 행의 열 집합이 같음. 명세 columns의 필수 열이 모두 있고 명세에 없는 열이 없음
그림 명세에 figures가 있거나 결과에 그림이 있으면 받은 파일이 PNG 서명으로 시작하고 2,000바이트보다 크며 SHA-256이 산출물 목록의 해시와 같음
출처 기록 provenance의 skill_id가 같음. skill_version이 등록부 버전과 같음. r_function·packages·params_hash·r_version이 있음
  • 표 형식 판정은 명세의 열 표기를 정규식으로 바꿔서 함(섹션 4.4)
    • <설명>은 .+가 됨
    • A | B 꼴로 나눈 대안은 그중 하나와 맞으면 됨
    • 끝에 ?가 붙은 열은 없어도 됨
  • 행이 없는 빈 표와 columns가 없는 표는 열을 확인하지 않음
  • 명세의 표 가운데 일부가 결과에 없는 것은 문제 삼지 않음(표가 하나도 없으면 부적합)
  • 명세에 없는 이름의 표가 결과에 있으면 부적합

15.2 입력 오류 판정

  • 실행기는 명세의 입력 정의와 첫 번째 예제 인자에서 오류 입력을 자동으로 만듦
  • 만들 수 있는 것만 만듦
종류 만드는 방법 기대 코드
없는 변수 예제 인자에 있는 첫 열 인자(column·column_list)의 값을 no_such_var로 바꿈(목록이면 첫 원소) E_COL_NOT_FOUND
필수 인자 누락 예제 인자에 있는 첫 필수 인자를 뺌 E_MISSING_PARAM
범위 밖 숫자 min이나 max가 있는 첫 integer·number 인자에 min − 1(없으면 max + 1)을 넣음 E_INVALID_VALUE
허용 밖 선택값 첫 enum 인자에 __not_allowed__를 넣음 E_INVALID_VALUE
형식 불일치 예제 인자에 있는 첫 dtype: numeric column 인자에 같은 데이터셋에서 아직 쓰지 않은 범주형(factor·문자) 변수를 넣음 E_TYPE_MISMATCH
  • 기대 action은 그 코드의 명세 errors 정의에서 가져옴. 없으면 실행 틀의 공통 정의에서 가져옴
  • 실행기가 확인하는 것
    • 오류 입력으로 계획을 제출해 HTTP 422로 거부되는지
    • 분석별 오류의 코드와 action이 기대와 같은지
    • message와 recovery_hint가 비어 있지 않은지
    • 그다음 같은 프로젝트에 예제 인자 그대로 다시 제출해 접수되는지(복구)

15.3 명세 작성 시 유의점

이 판정 방식에서 바로 나오는 규칙:

  • 결과표의 열 이름은 명세 columns와 문자 그대로 같아야 함
    • 열을 더하거나 이름을 바꾸면 명세도 함께 고침
  • 첫 예제는 성공해야 하고 필수 인자와 열 인자를 포함해야 오류 입력 시험이 만들어짐(섹션 4.7)
  • 숫자 인자의 허용 범위는 규칙보다 min·max로 적음
    • 입력 검증에서 E_INVALID_VALUE로 막힘
    • LLM 도구 정의에도 minimum·maximum으로 들어감
    • 범위 밖 숫자 시험도 자동으로 만들어짐
  • 입력 검증 공통 코드(E_COL_NOT_FOUND, E_MISSING_PARAM, E_INVALID_VALUE, E_TYPE_MISMATCH)의 action을 명세에서 바꾸면 기대 action도 그것을 따름
    • 바꿀 특별한 이유가 없으면 공통 정의와 같은 ask_user로 둠
